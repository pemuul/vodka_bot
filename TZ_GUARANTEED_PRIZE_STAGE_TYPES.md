## 0. Коротко: что просят и сколько это стоит

Восемь пунктов, присланных владельцем проекта, группируются в одну большую фичу —
**«гарантированный приз»**: новый тип этапа розыгрыша, где приз получает не случайный
победитель среди чеков-билетиков (как сейчас), а **каждый**, кто накопил нужный набор
товаров по чекам (в любом количестве чеков, в любом порядке — цитата из переписки: *«Человек
грузит сколько угодно чеков. Главное, чтобы в сумме было 2 позиции нужные»*). Это не
«доточить» существующую фичу авто-валидации — это новая бизнес-механика поверх неё, потому
что требует того, чего система сейчас **принципиально не делает**: копить прогресс участника
по нескольким чекам во времени.

| № | Пункт | Что это по сути | Объём |
|---|---|---|---|
| 1 | Поле «Тип» у этапа (Стандарт / Гарантированный приз) | 1 колонка в БД + переключатель в UI | **S** — маленький |
| 2 | «Правила проверки чеков» переезжают из акции в этап | Разбор существующей таблицы и API на связь по `stage_id` вместо `draw_id`; переезд UI-блока внутрь вкладки этапа. Переход **гладкий и автоматический** — старые правила копируются на все этапы своей акции одноразовой миграцией при старте (решение 11.1, раздел 4.2) | **L** — переезд кода/UI большой, плюс отдельная миграционная функция (не просто `ALTER TABLE`) |
| 3 | Сообщения по ходу выполнения условий + финальное поздравление | Требует «прогресса участника по этапу» (новая логика) **и** сообщения после **каждого** принятого чека, не только финального (уточнено из переписки, раздел 4.3) | **M/L** |
| 4 | Статус «Лишний чек» после выполнения условий | Новая проверка «уже победитель этого этапа» + новый статус + сообщение | **M** |
| 5 | Автопопадание в «Победители» + скрыть кнопку «Определить победителя» для этого типа | UI + запись в `prize_draw_winners` в момент завершения условий | **S/M** |
| 6 | Учитывать разные варианты подачи чеков (1 товар / несколько строк / кол-во в строке) | Извлечение позиций уже работает; новое — суммирование по правилу через несколько чеков пользователя | **M** — меньше, чем казалось в v1, т.к. извлечение данных уже готово |
| 7 | Ручная проверка: админ указывает товар, и **количество — только если у правила `min_quantity > 1`** (уточнено, раздел 11.8) | Новый UI в модалке чека + новый способ дописывать `receipt_items`, не затирая уже сохранённые | **M** |
| 8 | Для типа «Стандарт»: правила без min_quantity = алиасы правил, правила пустые = глобальные настройки | Уже реализованное поведение, нужно просто не сломать при переезде правил на уровень этапа | **S** — почти бесплатно |
| — | *(новое из переписки)* Отображение статуса в «Мои чеки» для тех, кто уже выиграл | Небольшая доработка `heandlers/menu.py`, раздел 4.9 | **S** |

**Итоговая оценка**: по-прежнему заметно больше, чем предыдущая доработка, потому что
появляется совершенно новая концепция — **накопительный прогресс участника по этапу**
(пункты 3, 4, 5, 6, 7 — грани одной этой концепции), и пайплайн обработки чека должен слать
не один, а несколько разных типов сообщений в зависимости от прогресса. Подтверждение того,
что не нужно показывать статистику «сколько уже выиграло» и не нужно менять смысл «Ошибка» —
немного уменьшает объём. Но требование «сообщение после каждого чека» (с текстом, зависящим от
остатка по товару, а не по чекам) и требование гладкой автоматической миграции старых правил
(вместо «админ пересоздаст руками») добавляют реальной инженерной работы обратно. Подробности —
раздел 12.

## 1. Термины

- **Акция / розыгрыш** = запись в `prize_draws` (даты, статус, авто-валидация).
- **Этап** = запись в `prize_draw_stages`, дочерняя к акции. Сейчас — просто «отдельный
  розыгрыш призов внутри акции» (у каждого этапа свой список победителей и текст рассылки),
  без разделения по типу и без своего периода времени.
- **Тип этапа** (новое, п.1) — `standard` (как сейчас: этап = случайный розыгрыш N
  победителей среди подтверждённых чеков акции) или `guaranteed_prize` (новое: приз получает
  каждый участник, накопивший нужное количество нужных товаров). **Подтверждено**: у одной
  акции этапы могут быть **любых и разных** типов одновременно, и каждый этап — независимая,
  уникальная сущность со своими правилами (раздел 11.2, 11.6). Это не редкий крайний случай,
  а прямо предусмотренная модель данных — реализация должна оценивать чек по **каждому**
  этапу акции независимо, а не «по одному этапу на акцию».
- **Правило** = запись в `prize_draw_rules` (название, SKU, алиасы через `;`, min_quantity,
  активность). Сейчас привязано к акции (`draw_id`), по п.2 привязывается к этапу (`stage_id`).
- **Прогресс участника по этапу** (новое понятие, вводится этим ТЗ) — для каждого активного
  правила гарантированного этапа: сумма `quantity` по всем позициям чеков (`receipt_items`)
  этого пользователя в рамках акции, которые сопоставились с этим правилом (по подтверждённым
  чекам, раздел 11.7). Этап считается выполненным, когда по **каждому** активному правилу
  накопленное количество ≥ `min_quantity`. Подтверждено (раздел 11, out-of-scope-но-важно):
  выиграть гарантированный этап можно только **один раз** — повторная победа/группировка
  нескольких побед в этой доработке не делается (см. non-goals, раздел 10).
- **«Победитель» гарантированного этапа** — запись в `prize_draw_winners` (та же таблица, что
  и для случайного розыгрыша), создаётся автоматически ботом в момент выполнения условий, а
  не рукой администратора по кнопке.

## 3. Центральное архитектурное решение (подтверждено владельцем)

### 3.1. Прогресс — без новой таблицы, через агрегирующие SQL-запросы

`receipt_items` уже хранит `receipt_id, raw_name, quantity, matched_rule_id` для каждого
чека. Правило (`prize_draw_rules`) принадлежит этапу (`stage_id`), чек знает пользователя
(`receipts.user_tg_id`) и акцию (`receipts.draw_id`). «Сколько пользователь накопил по
правилу X» — агрегирующий SQL-запрос:

```sql
SELECT receipt_items.matched_rule_id, SUM(receipt_items.quantity)
FROM receipt_items
JOIN receipts ON receipts.id = receipt_items.receipt_id
WHERE receipts.user_tg_id = :user_tg_id
  AND receipt_items.matched_rule_id IN (:rule_ids_этого_этапа)
  AND receipts.status = 'Подтверждён'          -- подтверждено, раздел 11.7
GROUP BY receipt_items.matched_rule_id
```

«Этап выполнен пользователем» = по каждому активному правилу этапа сумма ≥ `min_quantity`.

**Флаг «уже получил приз» — тоже без новой таблицы**, эту роль играет `prize_draw_winners`:
как только пользователь выполнил условия, бот сам вставляет туда строку (`stage_id`,
`user_tg_id`, `receipt_id` завершившего чека, `winner_name`). «Пользователь уже выиграл этот
этап» = `EXISTS(SELECT 1 FROM prize_draw_winners WHERE stage_id=? AND user_tg_id=?)`. Это
закрывает и п.5 (автопопадание в «Победители»), и даёт дешёвую проверку для п.4 («лишний
чек»).

Новые DAL-функции (`sql_mgt.py`, по образцу существующих):

```python
async def get_stage_rules(stage_id: int, only_active: bool = True, conn=None) -> list[dict]
async def get_draw_stages(draw_id: int, conn=None) -> list[dict]              # с полем stage_type
async def get_user_rule_progress(user_tg_id: int, draw_id: int, rule_ids: list[int], conn=None) -> dict[int, float]
async def is_stage_winner(stage_id: int, user_tg_id: int, conn=None) -> bool
async def add_stage_winner(stage_id: int, user_tg_id: int, receipt_id: int, winner_name: str, conn=None) -> None
```

### 3.2. Новый алгоритм сопоставления для гарантированного приза

Текущий `receipt_validation.match_items_to_rules()` спроектирован для модели «один чек — одна
проверка»: правило считается выполненным, если количество нужного товара **в этом самом
чеке** ≥ `min_quantity`. Для гарантированного приза семантика на уровне одного чека проще:
чек подтверждается, если в нём нашёлся хотя бы 1 товар по алиасам **любого** активного
правила этапа — количество в рамках одного чека не имеет значения, важна сумма по всем чекам
пользователя (цитата: *«Главное, чтобы в сумме было 2 позиции нужные»*, *«как он это

Это закрывает п.6 — 1 товар / несколько строк / количество в строке — всё это разные формы

OCR это «прям рандомно» — отсюда решение 11.3 (раздел ниже).

### 3.3. Этапы независимы и разных типов — подтверждено, не упрощаем

**Подтверждено владельцем** (11.2, 11.6): у акции могут одновременно быть этапы разных типов
(`standard` и `guaranteed_prize`), и каждый этап — уникальная сущность со своими правилами,
без объединения правил между этапами. Алгоритм обработки чека должен проверять его **против
каждого этапа акции по отдельности**:

```text
для каждого этапа акции (draw_stages):
    правила_этапа = get_stage_rules(stage.id)
    если этап.type == guaranteed_prize и правила_этапа не пусты:
        проверить чек по match_items_for_guaranteed_prize(items, правила_этапа)
    если этап.type == standard и правила_этапа не пусты:
        проверить чек по match_items_to_rules(items, правила_этапа)             # без изменений

если ни один этап с правилами не подошёл и есть хотя бы 1 стандартный этап без правил (или
акция вообще без этапов) → fallback на глобальные product_keywords (п.8, как сейчас)
```

Поскольку правило принадлежит ровно одному этапу (`prize_draw_rules.stage_id`), а
`receipt_items.matched_rule_id` фиксирует, по какому именно правилу засчитана позиция,
**прогресс по каждому этапу естественным образом изолирован** — не нужно, чтобы
`receipts.status` знал про «конкретный этап»: `receipts.status` остаётся общим флагом «бот
нашёл в чеке хоть один валидный товар» (`"Подтверждён"` / `"На ручной проверке"` / ...), а
то, какому именно этапу и правилу засчитан товар — хранится в `receipt_items.matched_rule_id`
и вычисляется через прогресс-запрос (3.1) отдельно на каждый этап.

**Единственное место, где нужен явный порядок проверки** — если один и тот же товар в чеке
одновременно подходит под правило `guaranteed_prize`-этапа и под правило `standard`-этапа.
Рекомендация: считать чек засчитанным для **обоих** этапов сразу (не выбирать «либо/либо») —
это соответствует модели «этапы независимы»: один и тот же реальный товар может одновременно
быть билетом лотереи и вкладом в гарантированный приз. Технически это означает, что при
сохранении `receipt_items` одна позиция может быть учтена для прогресса нескольких правил,
если у неё несколько совпадений (тогда `item_rule_map`/`matched_rule_id` должен уметь хранить
не одно, а несколько совпавших правил на позицию, либо, что проще, сохранять по одной строке
`receipt_items` на каждое совпавшее правило). Это единственная деталь реализации, требующая
осторожности при написании кода (не архитектурная развилка, а нюанс структуры данных).

### 3.4. Единое правило точного количества — для ОБОИХ типов этапа

**Важное уточнение владельца**: это не особенность гарантированного приза — это **общее
правило проверки чека для любого правила с `min_quantity > 1`, независимо от типа этапа**
(`standard` или `guaranteed_prize`). Формулировка: если чек не даёт точных данных о количестве
(QR не найден, ФНС недоступна/не ответила) и сработавшее правило требует больше 1 единицы
товара — такой чек **никогда** не подтверждается автоматически, только «На ручной проверке».

Для `standard` это уже действующее, а не новое поведение — `ocr_keywords_for_rules()`
(`receipt_validation.py:124-134`) уже фильтрует передаваемые в OCR алиасы по `min_quantity ==
1`, то есть OCR физически не может подтвердить правило с порогом больше 1. Это же поведение
**переиспользуется без изменений** и для правил `guaranteed_prize`-этапов — единая функция,
единая логика, никакого раздвоения кода по типу этапа.

Итого: `min_quantity == 1` (в любом типе этапа) → OCR-подтверждение разрешено при отсутствии
QR/ФНС. `min_quantity > 1` (в любом типе этапа) → без QR/ФНС всегда «На ручной проверке» —
OCR не даёт надёжного количества ни для лотереи, ни для гарантированного приза.

### 3.5. Новое: сообщение после каждого принятого чека, не только финальное

Из переписки с заказчиком (не было в исходном списке из 8 пунктов, но явно подтверждено как
«Принято»):

> *«Человек загрузил 1 чек с водкой — ему нужно прислать что-то в духе: "Чек принят. Остался
> ещё 1 товар для получения приза". Процедура повторяется до последнего чека. Человек загрузил
> последний чек с водкой — ему уже присылается финальное сообщение о победе.»*

То есть для этапа `guaranteed_prize` `notify_messages` (media_heandler.py:937-941) недостаточно
— обычное `"✅ Чек подтверждён"` для такого чека **не подходит**, нужно три разных исхода:

1. Чек подтверждён, но условия этапа ещё не выполнены целиком → сообщение с указанием, что
   именно ещё осталось (текст из переписки: «Остался ещё N товар(а/ов)»). **Важно: N — это
   остаток КОЛИЧЕСТВА ТОВАРА (штук), а не количество оставшихся чеков.** Пользователь мог
   закрыть весь остаток одним чеком (см. п.6) — считать, сколько чеков он загрузил, бессмысленно
   и неверно; считать нужно `min_quantity − уже накоплено` по каждому ещё не выполненному
   правилу этапа (раздел 3.1). Если правило одно и осталось ровно 1 шт. — получаем буквально
   исходный текст-пример; если правил несколько или остаток больше 1 — нужно перечислить остаток
   по каждому невыполненному правилу (название товара + сколько ещё штук), см. раздел 4.10.
2. Чек — тот самый, что закрывает все условия → финальное поздравление из исходного п.3 текста.
3. Чек «лишний» (условия уже выполнены раньше) → сообщение из п.4.

Это меняет заявленный в п.3 объём: одно статичное сообщение превращается в вычисляемый текст
с динамической частью «что и сколько ещё осталось по товару» (не по чекам). См. раздел 4.10 —
шаблоны текста хранятся в БД на уровне этапа (подтверждено, редактируемые поля).

а не просто перенести колонку.

**Алгоритм** (новая функция `sql_mgt.migrate_prize_draw_rules_draw_to_stage(conn)`, вызывается
из `create_or_update_tables()` **до** того, как для `prize_draw_rules` будет применена generic-
пересборка схемы):

```text
1. Если в текущей схеме БД у prize_draw_rules ещё есть колонка draw_id (а не stage_id) —
   миграция ещё не выполнялась, выполняем; иначе (колонка уже stage_id) — пропускаем (идемпотентно).
2. Прочитать все строки старой prize_draw_rules (draw_id, title, sku_code, aliases,
   min_quantity, is_active) — пока старая таблица ещё жива.
3. Для каждой строки: SELECT id FROM prize_draw_stages WHERE draw_id = <старый draw_id>.
   - Если у акции есть 1+ этапов → вставить КОПИЮ правила в новую таблицу для КАЖДОГО такого
     этапа (title/sku_code/aliases/min_quantity/is_active те же, новый stage_id).
     Это осознанно сохраняет прежнее поведение бит-в-бит: до этой доработки правила были
     общими на акцию и проверяли ЛЮБОЙ чек акции независимо от того, к какому этапу он мог бы
     относиться (этапы раньше вообще не влияли на проверку чека) — копирование правила во все
     существующие этапы акции воспроизводит ровно этот эффект после переезда на stage_id.
   - Если у акции 0 этапов (правила есть, а этапов ещё не создано — маловероятный, но
     возможный случай) → правило физически некуда привязать; строка не копируется,
     в лог пишется предупреждение с draw_id и названием правила, чтобы это было видно
     после деплоя. Это единственный случай, где нужен взгляд человека — но он не блокирует

4. Дать штатному механизму пересоздать таблицу prize_draw_rules по новой схеме (stage_id),

```

Это делает переход полностью автоматическим для нормального случая (у каждой акции есть хотя

**Второй реальный баг, найденный при живом тестировании через curl** (не покрывался pytest,
т.к. `site_bot/main.py` не имеет автотестов): пересчёт прогресса в `update_receipt()` был
дважды неправильно заблокирован условиями — (1) выполнялся только при СМЕНЕ статуса, поэтому
добавление ручной позиции к уже подтверждённому чеку никогда не проверяло победу повторно;
(2) весь блок пересчёта был вложен внутрь проверки «есть ли `message_id` и токен бота для
отправки уведомления», из-за чего для чека без `message_id` победа не фиксировалась вообще,
даже если условия выполнены. Оба случая воспроизведены вживую (curl, реальная БД) и
исправлены: пересчёт прогресса — это изменение бизнес-данных (`prize_draw_winners`), теперь
выполняется независимо от возможности отправить уведомление; условие пересчёта расширено на
«статус уже "Подтверждён" И только что добавлена ручная позиция».

Извлечение позиций чека (`_check_vodka_in_receipt()`, media_heandler.py:827-880) уже отдаёт
список `items` с `quantity` на каждую строку — случаи «1 товар», «несколько строк»,
«количество в строке» это просто разные формы одного и того же списка, дополнительно
разбирать их не нужно. Новое — только накопление через несколько чеков (раздел 3.1, 3.2).

**Явно, без двусмысленности** (это то же самое правило, что в разделе 3.4, повторено здесь,
потому что напрямую относится к формулировке п.6): если чек не даёт точных построчных данных —
**нет QR, либо ФНС недоступна/не вернула данные** — а нужное правило требует больше 1 единицы
товара (`min_quantity > 1`), такой чек **всегда** уходит на «На ручной проверке», никогда не
подтверждается автоматически. Автоматически (через OCR) можно подтвердить только правило с
`min_quantity == 1` — там неважно точное число, достаточно факта наличия товара. Это не новое
исключение для гарантированного приза — то же самое правило уже действует (и продолжает
действовать без изменений) для правил `standard`-этапов, раздел 4.8.

**Что считается «засчитывающим» прогресс** — подтверждено (11.7): только чеки со статусом
`"Подтверждён"`. Значит, при **ручном** подтверждении чека администратором тоже нужно
пересчитывать прогресс и при необходимости фиксировать победу — то есть бизнес-логика из
раздела 3.1/4.3 должна быть общей функцией, вызываемой и из автопайплайна
(`process_receipt()`), и из ручного изменения статуса (`update_receipt()`,
`site_bot/main.py:2100`).

**Пример из переписки, обязательный тестовый сценарий**: правило `min_quantity=3`, но в одном
чеке товар куплен сразу в количестве 3 (или больше) — должно засчитаться одним чеком, без
ожидания «ещё чеков» (сумма ≥ порога уже после первого чека). Предложенный алгоритм это
поддерживает автоматически, но стоит явно протестировать (раздел 8).

**Сложность**: основная часть работы — построить агрегацию прогресса и подключить её в оба
места, где меняется статус чека (автопайплайн и ручное подтверждение администратором).

**Статус: ✅ реализовано и проверено (2026-08-24).** `match_items_to_rules()` переиспользуется
БЕЗ ИЗМЕНЕНИЙ (не тронута) — источник правил сменился на `get_stage_rules(standard_stage.id)`.

**Уточнение владельца, важное для однозначности**: когда у `standard`-этапа заданы правила,
это **не** «в чеке есть подстрока-ключевое слово» — это точно то же самое строгое
сопоставление по алиасам, что и у `guaranteed_prize` (`match_items_to_rules()`,
`receipt_validation.py`). Смысл: «в лотерее участвуют только те, кто загрузил чек именно с
этим конкретным товаром (или набором товаров)», а не «у кого в чеке встретилось слово».
Поиск по ключевым словам (`product_keywords` из `/settings`, глобальные, без привязки к
конкретному товару/этапу) — это **отдельный, более простой режим**, доступный **только**
`standard`-этапу и **только когда у него вообще нет ни одного правила**. То есть у типа
`standard` де-факто два независимых режима проверки, а у `guaranteed_prize` — только один:

| | Есть правила у этапа | Правил нет |
|---|---|---|
| **`standard`** | Точный товар/набор товаров по алиасам правил (как у guaranteed_prize) | Общие ключевые слова сайта (`product_keywords`) — старое поведение без изменений |
| **`guaranteed_prize`** | Точный товар/набор товаров по алиасам правил (обязательно) | **Не имеет смысла** — без хотя бы одного правила невозможно посчитать прогресс/выполнение условия |

**Новое ограничение (следствие, не было явно в исходных 8 пунктах)**: этап типа
`guaranteed_prize` без единого правила никогда не сможет засчитать ни один чек и никого не
наградит — нужна защита в UI: при сохранении этапа с `stage_type = guaranteed_prize` и пустым
списком правил показывать предупреждение (или блокировать сохранение) в
`prize_draws.html`/`save_draw()`. Дёшево, но лучше поймать на этапе ввода, чем молча получить
неработающий этап.

**Правило про точное количество без QR/ФНС (раздел 3.4/4.6) одинаково для обоих режимов
`standard`**: если сработавшее правило имеет `min_quantity > 1`, а точных данных нет — «На
ручной проверке», это уже действующая логика (`ocr_keywords_for_rules()` фильтрует такие
правила из OCR), никакого нового кода для `standard` тут не требуется.

**Что реально меняется технически** (`process_receipt()`, `use_rules = bool(rules)`, 914;
`match_items_to_rules()` при `min_quantity <= 1` не требует точного количества,
`receipt_validation.py:84-88`) — источник правил: `rules = get_stage_rules(standard_stage.id)`
вместо `get_draw_rules(draw_id)`. Поскольку этапы независимы и правила у каждого свои
(подтверждено, 11.6), при нескольких `standard`-этапах акции проверка чека проходит по
правилам **каждого** такого этапа отдельно (раздел 3.3), без объединения — вопрос из версии 1
этого документа снят.

**Сложность**: низкая — по сути регрессионный тест плюс одна новая UI-валидация (пустые
правила у `guaranteed_prize`), а не новый алгоритм, при условии, что п.2 и раздел 3.3 сделаны

разные получатели (один человек здесь и сейчас vs все победители одним письмом позже), разное
время отправки. Смешивать эти два текстовых поля не стоит — делаем **два новых, отдельных,
необязательных поля** у этапа (используются только при `stage_type = 'guaranteed_prize'`):

```
prize_draw_stages.progress_message_text TEXT   -- "Чек принят. Осталось ещё: {remaining_items} 🎁"
prize_draw_stages.win_message_text TEXT         -- "Поздравляем🎉 Все условия выполнены..."
```

Оба поля — простой редактируемый текст в UI вкладки этапа (как `description`/`text_before`),
**без** конструктора шаблона со списком условий/циклов — но, как уточнил владелец, N в
промежуточном сообщении обязан быть **остатком количества товара**, а не числом чеков (раздел
3.5), а не «единица» по умолчанию — значит, нужен ровно один плейсхолдер, который код
вычисляет и подставляет: `{remaining_items}`.

**Как формируется `{remaining_items}`** (чистая функция в `receipt_validation.py`, например
`format_remaining_items(rule_progress: list[dict]) -> str`, где на вход — список ещё не
выполненных правил этапа с полями `title`, `min_quantity`, `progress`):

```text
для каждого правила этапа, где progress < min_quantity:
    remaining = min_quantity − progress
    "1 товар"                                — если правило одно и remaining == 1
    "{remaining} шт. «{title}»"              — если правило одно и remaining > 1
    "«{title}» — ещё {remaining} шт."        — построчно, если невыполненных правил несколько
```

Однопродуктовый случай с остатком 1 даёт буквально исходный текст-пример («Остался ещё 1
товар для получения приза»). Если поле `progress_message_text` у этапа пустое — используется
дефолтный python-текст, совпадающий с текстом из исходного ТЗ (дефолт хранится в коде, не в
DDL-строке БД — так надёжнее для многострочного текста с эмодзи). Поле `win_message_text` —
без плейсхолдеров, статичный текст; пустое поле → дефолт, дословно совпадающий с текстом
задания:

```
Поздравляем🎉
Все условия выполнены – значит, приз скоро будет вашим 🏆

Мы свяжемся с вами в ближайшее время, чтобы уточнить данные для отправки подарка 🎁

Спасибо, что вы с нами! 🫶🏻
```

Стоимость: 2 nullable-колонки + 2 текстовых поля в уже существующей вкладке этапа + одна
чистая функция форматирования остатка — даёт владельцу возможность менять текст без правки
кода, как уже сделано для `text_before`/`text_after`.

## 5. Полная схема изменений БД

```json
// prize_draw_stages — добавить 3 колонки (1 обязательная с default, 2 текстовых nullable)
"prize_draw_stages": "prize_draw_stages (id INTEGER PRIMARY KEY AUTOINCREMENT, draw_id INTEGER NOT NULL, name TEXT NOT NULL, description TEXT, winners_count INTEGER DEFAULT 1, text_before TEXT, text_after TEXT, order_index INTEGER DEFAULT 0, stage_type TEXT NOT NULL DEFAULT 'standard', progress_message_text TEXT, win_message_text TEXT, create_dt TIMESTAMP DEFAULT CURRENT_TIMESTAMP)"

// prize_draw_rules — draw_id заменяется на stage_id; старые данные переносятся автоматической
// миграцией (копия правила на каждый существующий этап акции), см. раздел 4.2 — не просто ALTER
"prize_draw_rules": "prize_draw_rules (id INTEGER PRIMARY KEY AUTOINCREMENT, stage_id INTEGER NOT NULL, title TEXT NOT NULL, sku_code TEXT, aliases TEXT NOT NULL, min_quantity INTEGER DEFAULT 1, is_active BOOLEAN DEFAULT TRUE, create_dt TIMESTAMP DEFAULT CURRENT_TIMESTAMP)"

// receipt_items, receipts, prize_draws, prize_draw_winners — без изменений
```

`stage_type`, `progress_message_text`, `win_message_text` — безопасные `ALTER TABLE ADD
COLUMN` (все `NULL`/`DEFAULT` совместимы со старыми строками). `prize_draw_rules.stage_id` —
единственная колонка в этой доработке, которая требует **не** декларативного ALTER, а
написанной вручную одноразовой миграционной функции (раздел 4.2), потому что новое значение
(`stage_id`) нужно вычислить из старого (`draw_id` → этапы этой акции), а не просто скопировать.

Новых таблиц не требуется (раздел 3.1).

## 6. Новый pipeline обработки чека (было → стало)

### Было (после `fa6482c`)

```text
set_photo(): draw_id → auto_validation → add_receipt(status) → enqueue (если включено)
process_receipt():
  rules = get_draw_rules(draw_id)                      # по акции
  QR найден → дубликат? → ФНС → match_items_to_rules (в рамках ОДНОГО чека)
      confirmed → "Подтверждён"; иначе → "На ручной проверке" (если есть rules)
                                        → "Нет товара в чеке" (если rules нет, legacy)
  QR не найден / ФНС недоступна → OCR (только min_quantity==1 правила)
      confirmed → "Подтверждён"; иначе → "На ручной проверке"/"Ошибка" (legacy)
```

### Должно стать

```text
set_photo():
  draw_id → guaranteed_stages = все этапы акции с типом guaranteed_prize (может быть 0, 1, много)
  если guaranteed_stages не пуст и пользователь уже is_stage_winner() во ВСЕХ них:
      add_receipt(status="Лишний чек") → сообщение из п.4 → НЕ enqueue, конец
  иначе: как раньше (auto_validation → статус → enqueue)

process_receipt():
  на входе повторно проверить "лишний чек" (защита от гонки) → если да, статус "Лишний чек", конец
  stages = get_draw_stages(draw_id)                       # оба типа, каждый со своими правилами
  для каждого guaranteed_prize-этапа с активными правилами:
      QR+ФНС → match_items_for_guaranteed_prize(items, правила_этапа)
          нашёлся товар → save_receipt_items(..., matched_rule_id=правило.id)
                          прогресс = get_user_rule_progress(user, draw_id, rule_ids этапа)
                          все правила этапа выполнены и not is_stage_winner →
                              add_stage_winner(...) → финальное "Поздравляем..." (п.3/3.5)
                          иначе →
                              "Подтверждён" + промежуточное "Чек принят. Осталось..." (3.5)
          не нашёлся (или min_quantity>1 без QR/ФНС, раздел 3.4) →
              если это единственный релевантный этап → "На ручной проверке"
              иначе → попробовать остальные этапы (standard/другие guaranteed) ниже

  для каждого standard-этапа с активными правилами (или fallback на product_keywords, если
  правил вовсе нет ни у одного этапа акции) → СТАРАЯ логика match_items_to_rules, без изменений

  если ни один этап чек не подтвердил и не отправил на ручную проверку →
      "Ошибка" (только техническая — нечитаемый файл/сбой, как и сейчас; смысловые расхождения
      QR/OCR ведут в "На ручной проверке", решение 11.5 оставляет текущее поведение здесь)
```

### Ручное изменение статуса администратором (`update_receipt()`, новое)

```text
update_receipt(receipt_id, status, manual_item=None):
  если manual_item передан: add_manual_receipt_item(...) (не стирая существующие ФНС-позиции);
      количество обязательно, только если правило.min_quantity > 1 (решение 11.8)
  если status меняется на "Подтверждён" и у чека есть акция с guaranteed_prize-этапом:
      пересчитать прогресс (та же функция, что в process_receipt)
      при выполнении условий — add_stage_winner(...) + финальное сообщение "Поздравляем..."
      иначе — обычное уведомление о подтверждении (без "Поздравляем")
  как раньше: отправить пользователю уведомление о смене статуса
```

## 9. Риски

- **Основной риск — регресс уже работающей на проде логики `standard`/лотереи.** Любая
  правка `process_receipt()` должна оставить существующий сценарий (акция без этапов
  гарантированного приза) работающим бит-в-бит как сейчас.
- **Одна позиция чека, подходящая под правила двух разных этапов одновременно** (раздел 3.3)
  — решение «засчитывать в оба» требует, чтобы структура `receipt_items`/`item_rule_map`
  поддерживала более одного совпавшего правила на одну товарную позицию; это нюанс структуры
  данных, не архитектурная развилка, но легко упустить при реализации «в лоб».
- **`site_bot/main.py` автозагружает SQLAlchemy-таблицы при импорте** — после миграции нужен
  перезапуск процесса `vodka_site` (известный паттерн, память `site_autoload_restart_race`).
- **Объём UI-правок в `prize_draws.html`** — блок правил переезжает из «одного на акцию» в
  «один на этап»; при нескольких этапах в модалке это качественно больше DOM-состояния для
  ручного JS без реактивности — выше риск багов синхронизации UI, чем при плоской структуре.
- **Миграция `prize_draw_rules.draw_id → stage_id`** (раздел 4.2) — единственное место в
  проекте, где схема БД меняется не декларативно через `table_shem.json` + автоматический
  ALTER, а написанной вручную функцией. Она должна быть атомарной (одна транзакция) и
  идемпотентной (безопасный повторный запуск при рестарте до полного применения) — иначе есть
  риск дублирования или частичной потери правил при сбое посередине операции.
- **Дублирование правил на несколько этапов акции** (миграция копирует правило в КАЖДЫЙ
  существующий этап) может дать администратору неожиданно много одинаковых правил в разных
  вкладках, если у акции их было несколько ещё до этой доработки — поведенчески корректно
  (сохраняет старый эффект), но стоит предупредить владельца, что после деплоя стоит один раз
  просмотреть получившиеся правила по этапам (не обязательное действие, а рекомендация).

## 10. Что не делаем (в рамках этой оценки объёма)

- Не переносим SQLite на другую БД, не меняем стек (aiogram 3, FastAPI, SQLite, Jinja2).
- Не добавляем таблицу «прогресс» — считаем на лету агрегирующими запросами.
- Не переписываем `fns_api.py`, `ocr.py`.
- **Не делаем повторную/множественную победу одного пользователя в одном этапе** — подтверждено
  явно (переписка: «в этой доработке делаем так, что может участвовать только 1 раз»).
  Группировка нескольких побед («как мы группируем выигрыши») — отдельная будущая доработка,
  сознательно отложена.
- Не строим статистику «сколько человек уже выполнили условия» в UI акции (решение 11.4).
- Не меняем поведение статуса «Ошибка» для старого режима без правил (решение 11.5).
- Не показываем пользователю прогресс «X из Y нужных товаров» в «Мои чеки», пока не
  запрошено отдельно (раздел 4.9).

## 12. Оценка объёма относительно предыдущей доработки

Предыдущая доработка (`TZ_ACTION_VALIDATION_SETTINGS.md`) добавляла: 1 колонку в существующую
таблицу + 2 новые таблицы + один новый модуль без внешних зависимостей + точечные правки
одного пайплайна, без изменения модели данных «чек = независимый билет».

Эта доработка меняет саму модель данных (межчековый прогресс), требует переноса кода недавно
выкаченной прод-функциональности на новый уровень связи **с автоматической миграцией данных**
(раздел 4.2 — не декларативный `ALTER`, а написанная вручную одноразовая функция), добавляет
новую ветку логики в критичный пайплайн с **тремя** разными исходами сообщений вместо одного
статичного, где текст ещё и вычисляется по остатку товара (раздел 3.5/4.10), требует новую
точку интеграции бизнес-логики победы в ручном админском флоу (`update_receipt()`), и заметно
больше UI-работы (`prize_draws.html` — правила на каждый этап + шаблоны текстов; `receipts.html`
— условный ввод количества; `menu.py` — баннер в «Мои чеки»).

Подтверждённые решения слегка снижают объём в паре мест (не нужна статистика победителей, не
нужно менять смысл «Ошибка»), но требование гладкой автоматической миграции правил (вместо
«админ пересоздаст руками») и требование «сообщение после каждого чека с остатком по товару»
(раздел 3.5) добавляют реальной инженерной работы обратно — итоговая оценка объёма не
уменьшилась по сравнению с первой прикидкой, а по факту чуть выросла (см. точные часы —
раздел 13). Ориентировочно **в 2–2.3 раза больше кода и заметно выше риск регресса**, чем в
предыдущей доработке, в первую очередь из-за пунктов 2 (переезд правил + миграция данных), 6/7
(накопительный прогресс + ручной ввод) и 3/3.5 (многоступенчатые сообщения с вычисляемым
текстом).

## 14. Запрет на самостоятельный деплой / push на production

Как и во всех предыдущих ТЗ этого проекта: реализационная нейросеть **не должна**
самостоятельно выкатывать изменения на продовый сервер (217.198.6.100 / finskyice.com,
`/home/VodkaBot`, supervisor-процессы `vodka_bot`, `vodka_site`, `vodka_bot_check`; боевая БД
`/home/VodkaBot/tg_base.sqlite`) — включая `git push` в `main`, `git pull`/перезапуск
процессов на сервере, запуск миграций на проде, любые правки прод-БД. Отдельно важно здесь:
миграция `prize_draw_rules` (раздел 4.2) автоматическая и не требует ручных действий владельца
после выкладки — но именно поэтому она должна быть заранее прогнана и проверена на **копии**
прод-БД перед реальным деплоем (раздел 15), а не «как получится» на бою: это нестандартная,
написанная вручную миграция, а не декларативный `ALTER TABLE`, и это единственное место в
доработке, где ошибка молча испортит боевые данные без возможности откатить одной командой.

Разрешено: изучать проект, работать локально, готовить патч в отдельной ветке, писать код без
выкладки, запускать локальные тесты (`pytest`, локальная SQLite), подготовить (но не
выполнять) инструкцию по деплою для показа владельцу.
