# Выкладка: ответы пользователю по чеку

Ветка `fix/receipt-notifications`. Выкатывает владелец проекта — ни один шаг отсюда не
выполнен заранее.

Занимает 10–15 минут, из них простой сервисов — меньше минуты.

---

## Что меняется в поведении

| Было | Стало |
|---|---|
| «На ручной проверке» и «Ошибка» — пользователю ничего | Приходит сообщение, что чек проверит сотрудник |
| Чек ждёт человека — в колокольчике пусто | Чек попадает в уведомления администратора |
| Принятый чек — «✅ Чек подтверждён» | Приходит текст, настроенный в карточке этапа, с числом попыток |
| Ответы воркера не видны в чате участника | Видны, как и все остальные сообщения |
| Этап не переключается по датам | Переключается сам, не чаще раза в 5 минут |
| Отправленное сообщение уже не изменить | Сохраняется его telegram-id |

Два изменения заметит пользователь: чек, ушедший на ручную проверку, больше не остаётся
без ответа, а принятый чек отвечает настроенным текстом вместо стандартного. Оба —
по плану, но предупредите владельца до выкладки.

---

## Порядок

### 1. Бэкап

```bash
cd /home/VodkaBot/vodka_bot

```

Скрипт кладёт в `/home/VodkaBot/backups/<метка>/` снимок базы (через `.backup`, сервисы
останавливать не нужно), счётчики строк, прогресс участников активного этапа, текущий

есть — на сервере лежит незакоммиченный патч (исторически так жили секреты веб-панели),
и `git checkout` его затрёт. Разберитесь с ним до продолжения.

### 4. Применить миграцию

Отдельной команды не нужно: миграцию применяет воркер при старте. Порядок важен — панель
читает схему базы один раз при запуске, поэтому её поднимаем последней, иначе она не увидит
новых колонок и не будет сохранять id отправленных сообщений.

```bash
supervisorctl start vodka_bot_check
sleep 10

# колонки и индекс на месте?
sqlite3 /home/VodkaBot/tg_base.sqlite "PRAGMA table_info(participant_messages);" | grep -E "tg_message_id|receipt_id"
sqlite3 /home/VodkaBot/tg_base.sqlite "SELECT sql FROM sqlite_master WHERE name='idx_participant_messages_receipt';"
```

Ожидается две строки колонок и индекс с хвостом `WHERE receipt_id IS NOT NULL`.

Миграция — только `ALTER TABLE ADD COLUMN` и частичный индекс: данные не переписываются,
на базе в 98 МБ отрабатывает мгновенно и добавляет около 4 КБ. Прогнана на копии боевой
базы: 2305 чеков, 110 504 сообщения, 12 334 пользователя — ни одна строка не потерялась,
`integrity_check` = ok.

### 6. Проверить

```bash
# счётчики совпадают с теми, что записал бэкап
sqlite3 /home/VodkaBot/tg_base.sqlite "
  SELECT 'receipts', count(*) FROM receipts
  UNION ALL SELECT 'participant_messages', count(*) FROM participant_messages

  JOIN prize_draw_rules pr ON pr.id = ri.matched_rule_id
  JOIN prize_draw_stages s ON s.id = pr.stage_id AND s.status = 'active'
  WHERE r.status = 'Подтверждён' GROUP BY r.user_tg_id ORDER BY r.user_tg_id;") \
  /home/VodkaBot/backups/<метка>/active_stage_progress_before.txt

# активный этап не потерялся

# в логах нет падений

```

Прогресс участников должен совпасть строка в строку. На момент подготовки на активном
этапе пять участников: `5`, `2`, `1`, `1`, `1` попытки.

### 7. Живой прогон

Пришлите боту чек с продукцией HARD TEA и проверьте **и в Telegram, и в чате участника
в панели** — расхождение между ними и было исходной жалобой:

- [ ] чек с HARD TEA → «Чек принят ✅ / Сейчас у вас 1 попытка выиграть 🎟️», и это видно в панели;
- [ ] второй такой же чек → «2 попытки выиграть»;
- [ ] чек без нужного товара → «❌ В чеке не найден нужный товар», видно в панели;
- [ ] фото без читаемого QR → сообщение о ручной проверке, и чек появился в колокольчике;
- [ ] тот же чек повторно → «❌ Чек уже загружен»;
- [ ] подтверждение чека из панели → ровно одно сообщение с верным числом попыток;
- [ ] `sqlite3 ... "SELECT id, text, tg_message_id, receipt_id FROM participant_messages WHERE receipt_id IS NOT NULL ORDER BY id DESC LIMIT 5;"` — id сохраняются.

### 8. Через сутки

```bash
# ни одного чека без ответа
sqlite3 /home/VodkaBot/tg_base.sqlite "
SELECT r.id, r.user_tg_id, r.status, r.create_dt FROM receipts r
WHERE r.create_dt >= datetime('now','-1 day')
  AND NOT EXISTS (SELECT 1 FROM participant_messages m
                  WHERE m.user_tg_id = r.user_tg_id AND m.sender='admin'
                    AND m.timestamp > r.create_dt
                    AND (m.text LIKE '%принят%' OR m.text LIKE '%подтвержд%'
                         OR m.text LIKE '%не найден%' OR m.text LIKE '%проверит наш сотрудник%'));"

# подавленных противоречий быть не должно
grep -c "противоречивое сообщение подавлено" /var/log/vodka_bot/err_check.log
```

Первый запрос должен вернуть пусто. Второй — ноль; если больше, значит статус и прогресс
где-то расходятся, и это надо разбирать (пользователю при этом ушёл нейтральный текст, а не
бессмыслица).

## Откат

```bash
ROLLBACK_DB=0 bash deploy/rollback_prod.sh <метка>    # обычный случай: только код
bash deploy/rollback_prod.sh <метка>                  # если пострадали данные
```

Миграция только добавляет колонки, старый код их не замечает — поэтому почти всегда
достаточно откатить код. Восстановление базы стирает всё, что пользователи прислали после
бэкапа, поэтому это крайняя мера; скрипт перед перезаписью сам делает снимок текущей базы.

## Отдельно, не входит в выкладку

**Семь чеков в статусе «Ошибка» от 07.06–16.06.** После выкладки они по-прежнему будут
висеть в колокольчике. Они из завершённых акций. Рекомендую удалить их через панель:
смена статуса сейчас отправит тем пользователям сообщение спустя три месяца, а удаление —
нет.

```
638, 639, 640, 738, 956, 1092, 1557
```

**Позиции чеков 2615, 2621, 2632** ссылаются на правила 10 и 15, которых больше нет
(наследие бага с пересозданием id, починенного 31.08). Этапы завершены, на текущую акцию не
влияют — чистить не обязательно.

**Java для `pyzxing`.** На сервере нет JRE, поэтому третий способ распознавания QR молча не
работает (`java: not found` в логе на каждый чек без QR). Установка `default-jre` вернёт его
и уменьшит поток чеков, уходящих на ручную проверку. Отдельным решением: это +150 МБ на
диск и новая зависимость в рантайме.

**Ограничение Telegram.** Сохранённые `tg_message_id` позволяют удалять и редактировать
отправленные сообщения, но Telegram разрешает боту удалять свои сообщения только в течение
48 часов после отправки. Поэтому хранить эти ссылки дольше нескольких дней смысла нет — если
таблица начнёт мешать, безопасно чистить `tg_message_id` у записей старше недели.
